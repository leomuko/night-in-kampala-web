# Catalogue data and permissions

The catalogue uses separate documents for public reads and staff work. The public projection copies only shopper-facing fields from a validated draft. Clients cannot write Firestore documents, including when signed in as staff or owner. Staff actions call Functions that check claims, validate input and write through the Admin SDK.

| Path | Reads | Data contract |
| --- | --- | --- |
| `products/{slug}` | Everyone, when `status` is `published` | Stable slug, name, item code, category ID, whole UGX price, stock type, size label and size filter keys, measurements in cm, condition, rework and care, public availability, first publication time, image revision, ordered photo renditions, share metadata and illustrative stock marker. |
| `productDrafts/{slug}` | Staff and owner | Recoverable editor fields, proposed media references and editable details. Drafts may exist while a previously published revision is live. |
| `inventory/{slug}` | Staff and owner by product ID | Private available quantity and stock model. Repeatable pieces retain exact quantities by variant. Trusted stock writes update the corresponding public availability and audit record atomically. |
| `auditLogs/{entry}` | Owner | Append-only audit events written by the server, including actor UID, action, product ID, timestamp and relevant changes. |
| `catalogueSettings/categories` | Everyone by document ID | Ordered `items` with stable `id`, editable `label` and `active` flags. Deactivated entries stay readable so existing references resolve. The editor and filters use active entries for new choices. |
| `catalogueSizes/{key}` | Public labels, with query limit at most 24 | Sizes on real, published, requestable stock with positive units. Private counters track how many products contribute each size. |
| `contentDrafts/{collection--slug}` | Staff and owner | Editable title, copy, content-type fields and revision. Save and publish are distinct operations. |
| `collections/{slug}`, `events/{slug}`, `lookbooks/{slug}` and `pages/{slug}` | Everyone, when `status` is `published` | Published editorial fields. Drops carry ordered public product slugs and a cover reference. Events carry city, Upcoming/Past and optional venue and calendar date. Lookbooks and pages can reference a product cover and validated same-site links. |
| `orders/{id}` and other private collections | Denied by default | Order access rules will be defined with the ordering workflow. |

The claims are Boolean `staff: true` and `owner: true`. A user document or a string claim grants no staff permissions. The staff provisioning command creates demo identities. The explicit mapping in `functions/catalogue-projection.js` copies shopper-facing fields, builds versioned media paths from IDs and never accepts a client purchase flag. Phase 3 entry task A1 adds explicit owner approval on a saved revision. The server derives the public `purchasable` indicator from real-stock approval, published status and Available/Requested state. The order service must recheck those facts at submission. The trusted publisher validates the category, stock state, processed media and required fields before writing it. Use stable public item codes that contain no supplier or customer data.

The emulator seeder creates the category document from illustrative defaults only if it is missing. Staff can rename and retire categories while keeping IDs stable and existing product references readable.

## Indexed reads

Every public product list uses `where('status', '==', 'published')` and a limit of at most 24. The shop can combine category ID and availability equality filters with a single `array-contains` size filter. Supported sorts are newest first by `publishedAt` and price ascending or descending by `priceUGX`. Use the last document snapshot as the cursor so tied values keep Firestore's document ID ordering. The homepage displays the three newest published pieces. Shop filters apply on change and keep their values in the URL. The size options come from `catalogueSizes`. Approval, publication, withdrawal and stock changes update these options in the same transaction as the product. The archive sets availability to `sold` and retains the published constraint. Public editorial list reads use the same publication predicate and 24-document cap. Drop details read up to 24 referenced products, in saved order, and omit withdrawn pieces. `firestore.indexes.json` contains the composites for these shapes. Local tests cover query permissions and cursor behavior. The Firestore emulator does not enforce composite indexes. [Firestore query rules](https://firebase.google.com/docs/firestore/security/rules-query) and [emulator differences](https://firebase.google.com/docs/emulator-suite/connect_firestore#how_the_cloud_firestore_emulator_differs_from_production).

## Media

Uploaded sources retain their original classification. Unclassified historical photos and explicitly illustrative or generated uploads are ineligible for real-stock approval. Uploading a photograph of the actual piece and approving the saved revision require truthful classification and owner review. The software enforces recorded provenance and cannot determine an arbitrary image's origin from its pixels. Replacing images or changing saved details creates a new revision that needs owner approval.

- `product-drafts/{slug}/{uid}/{photoId}.jpg` or `.webp` holds the browser-compressed original. A staff member or owner can create objects under their own UID for an existing draft. Reads require a staff or owner claim. Use a fresh photo ID when replacing a photo. Clients cannot list, overwrite, change metadata or delete objects. Rules bound declared image type and bytes to JPEG/WebP, non-empty and at most 2 MiB. The browser compresses images to these bounds and the server independently decodes and validates the actual file.
- `product-media/{slug}/{revision}/{photoId}-{320,640,1280}.webp` and `product-media/{slug}/{revision}/share.jpg` hold server-processed public media. Only the revision named by the published projection can be read through Storage rules. Uploads to this namespace are server-only. Publication prepares the immutable rendition files first, then switches the projection to that revision. Withdrawal changes the projection status and closes origin access.
- Use authenticated SDK reads for private preview blobs and avoid saving or sharing Storage download-token URLs. A trusted handler serves same-origin `/media/products/...` URLs, checking publication and the active revision and returning an immutable cache header for a successful versioned request. Draft objects remain private and copy operations omit download-token metadata. Already downloaded or cached copies may persist. Cloud permissions and CDN behavior remain staging checks. [Storage rule conditions](https://firebase.google.com/docs/storage/security/rules-conditions) and [direct SDK downloads](https://firebase.google.com/docs/storage/web/download-files#download_data_directly_from_the_sdk).

Run `npm run test:rules` with the main emulator suite stopped. The rule tests run Firestore and Storage in the same isolated demo project so Storage's document lookups read the seeded rule fixtures. The tests cover public and private reads, role claims, protected writes, upload scope and limits, and media visibility after a revision switch or unpublish.

## Prelaunch data in the shared project

Treat preview stock, editorial content, orders and logins as disposable. Keep launch content and credentials out of the preview test. The preview backend marks new product and editorial drafts, public projections and orders with `isTestData: true`. The queue inherits the order marker. Approval leaves the test marker in place even where it allows a photographed test piece to exercise checkout. Live order submission rejects marked stock. An order line records whether its piece was real catalogue stock at submission. Unpurchasable products with `isRealCatalogueStock: false` and illustrative editorial records are identifiable even without a preview marker.

Add the Boolean custom claim `testAccount: true` alongside the role when provisioning a test Auth account with trusted admin tooling. The local provisioning and seed scripts do this automatically. Keep the permanent owner account separate. An email address or role alone does not identify a test account.

Draft uploads use `product-drafts/<slug>/`. Trusted processing derives `product-processed/<slug>/` and versioned publication uses `product-media/<slug>/`. Processed and published media for marked pieces also carry server-written `nikTestData=true` object metadata. Use the slug and associated draft or product to identify raw uploads and older renditions. Unpublished drafts without a public counterpart are prelaunch cleanup candidates. A retained genuine product keeps its source files for future edits. Review categories and shared owner settings separately before launch.
